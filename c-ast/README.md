# C AST — пошаговый лексер и парсер на Nexus

Это **отдельное приложение** в `c-ast/`, рядом с `examples/`. Проект импортирует `nexus/core` как готовый пакет из `c-ast/node_modules/nexus`, а не из `../src/core`.

В отличие от старой версии, **основной путь не вызывает `lex(source)` или `parseTokens(tokens)`**. Nexus управляет реальными переходами лексера и синтаксического анализатора: состояние автоматов находится в `Store`, а новые порции работы запрашиваются с помощью `Event`.

## Windows PowerShell

В корне проекта Nexus (сначала соберите пакет и установите его содержимое в приложение):

```powershell
npm ci
npm run build
npm run prepare:examples
npm run c-ast:parse -- .\c-ast\fixtures\factorial.c
npm run c-ast:parse -- .\c-ast\fixtures\factorial.c .\output\factorial.json
npm run c-ast:parse -- .\c-ast\fixtures\factorial.c --stdout
npm run c-ast:parse -- .\c-ast\fixtures\factorial.c --trace
npm run c-ast:parse -- .\c-ast\fixtures\factorial.c --batch-size=1
npm run c-ast:steps
npm run c-ast:test
```

Для полноценной автономной установки зависимостей C AST выполните `npm --prefix c-ast ci` после создания корневого `nexus-0.1.20.tgz`. В `c-ast/package.json` закреплена зависимость `"nexus": "file:../nexus-0.1.20.tgz"`, и при компиляции используются только публичные типы пакета. Для использования отдельно от этого репозитория замените локальный путь к `.tgz` на путь к скачанному GitHub Release или прямую ссылку на релиз.

Файл `factorial.ast.json` появляется рядом с входным `.c`, если не указан другой выходной путь. `--trace` печатает сведения о **зафиксированных** токенах и AST-узлах в `stderr` (это не портит JSON в `stdout`). `--batch-size=N` настраивает количество машинных переходов, выполняемых за один Commit.

## Что является реактивным вычислением

```text
CLI: входной .c
  |
  v
Event<SourceInput> --[Start Handler]--> Store<LexerMachineState>
  |
  v
Event<LexPulse> --[Lex Handler]--> advanceLexer(state)
  |                                |  один токен за переход
  |<-------- повторное emit --------|  Store<LexerMachineState>
  |
  +-- EOF --> Store<ParserMachineState> + Event<ParsePulse>
                                           |
                                           v
                               [Parse Handler] -> advanceParser(state)
                                           |       одна грамматическая инструкция
                               Store<ParserMachineState>
                                           |
                                emit(ParsePulse) до завершения
                                           |
                                     завершено
                                           v
                               Store<TranslationUnit>
                                           |
                                    Event<AstReady>
                                           |
                                    [Metrics Handler]
                                           v
                                   Store<AstMetrics>
                                           |
                                           v
                                       JSON AST
```

**Граница транзакции:** `Handler.run()` считывает ранее зафиксированное состояние, выполняет ограниченную порцию переходов, подготавливает **новый** экземпляр состояния и, если работа не окончена, отправляет следующий `Pulse`. Только после успешного Commit новые сигналы становятся видимы. При ошибке синтаксиса записывается отдельное состояние `failed`, продолжение не отправляется.

`batchSize` по умолчанию 24. Один вызов `advanceLexer()` производит максимум один токен (включая пропуск предшествующих пробелов/комментариев), один вызов `advanceParser()` выполняет **одну инструкцию грамматического автомата**. Один `Handler.run()` выполняет до `batchSize` таких переходов перед Commit; это намеренная пакетная оптимизация. Вариант `batchSize: 1` максимально подробен, но медленнее.

### Где хранится продолжение парсера

`ParserMachineState` имеет явные `cursor`, `tasks` (стек операций грамматики), `values` (стек частичных AST-значений), `status`, `transitions` и `ast`. Ни один долгоживущий стек рекурсивных JS-вызовов или Generator не используется. Это позволяет делать остановку **между переходами**, сохранять промежуточное состояние и проверять его независимым тестом.

`c-ast/language/` разделён по ответственности:

- `lexer-machine.ts`: неизменяемый лексический курсор и один переход получения токена. Токены накапливаются в связанной цепочке, без копирования массива на каждом шаге.
- `parser-vm.ts`: операции с одним стеком продолжений и одним стеком значений; черновик одного перехода.
- `grammar-declarations.ts`: единица трансляции, объявления, параметры и декларации переменных.
- `grammar-statements.ts`: блоки, `if`, циклы, `return` и объявления в блоке.
- `grammar-expressions.ts`: приоритеты, унарные/бинарные/условные выражения, вызовы и индексирование.
- `parser-machine.ts`: диспетчер одной грамматической инструкции; не разбирает весь исходник.
- `ast.ts`: схемы JSON AST и метрики.
- `lexer.ts` / `parser.ts`: **только независимый эталон старого алгоритма** для проверки совпадения; основной Nexus-путь их не импортирует и не вызывает.

`c-ast/nexus/create-c-parser.ts` — слой интеграции из четырёх независимых Handler (Start, Lex, Parse, Metrics). Он не содержит грамматических правил. `c-ast/cli/` занимается только чтением, записью и диагностикой.

## API: автоматически и вручную

```typescript
import { createCParser } from './c-ast';

const parser = createCParser({
  batchSize: 8,
  maxTransitions: 2_000_000,
  onToken: token => console.log('TOKEN', token.kind, token.text),
  onNode: node => console.log('NODE', node.kind, node.span.start.line),
});

try {
  // Автоматический реактивный прогон (синхронный inline).
  const result = parser.parse('int f(){return 2+3*4;}');
  console.log(result.ast, result.metrics);

  // Пошаговый режим; остановка — просто прекращение вызовов advance().
  parser.begin('int f(){return 7;}');
  parser.advance(1);                  // один токен
  parser.advance(4);                  // ещё до четырёх переходов
  const progress = parser.progress(); // stage, tokens, cursor, stackDepth...
  console.log(progress);
  const completed = parser.resume();  // автоматически до завершения
  console.log(completed.ast);
} finally {
  parser.dispose();
}
```

Переход от `lexing` к `parsing` производится только после получения EOF. В ручном режиме `advance(1)` во время лексинга строит один токен, а во время парсинга исполняет одну грамматическую инструкцию; переключение этапа само по себе не исполняет инструкцию следующего этапа. Прогресс можно наблюдать между вызовами. `resume()` завершает **синхронную** inline-цепочку, так что не освобождает поток JS на время работы. Для длительных вычислений нужен отдельный deferred-вариант исполнительного цикла.

`onToken` и `onNode` являются необязательными post-commit наблюдателями; их данные отделены от внутренних мутабельных объектов автомата. Исключение в наблюдателе может прервать дальнейшее inline-распространение (`PostCommitReactionError`), поэтому для штатной работы callback должен быть надёжным.

## Поднабор C

Поддерживается тот же синтаксис, что в предыдущем эксперименте: примитивные типы и квалификаторы, переменные, указатели, массивы, функции/прототипы, блоки, `if/else`, `while`, `do/while`, `for`, `return`, `break/continue`, вызовы, операции присваивания, унарные/бинарные выражения, тернарный оператор, доступ к полям, индексирование, комментарии, числовые и строковые литералы. Поддерживаются span-координаты (`offset`, `line`, `column`). Директивы `#include/#define` представлены текстовыми узлами AST и **не обрабатываются препроцессором**.

Не являются реализованными: полный C11/C17, семантическая проверка типов, `typedef`, `struct/union/enum`, `switch`, `goto`, указатели на функции и C-препроцессор. Например, `return;` грамматически допускается, а проверка его допустимости в не-void функции — отдельная семантическая задача.

## Гарантии и границы

- Изменения в `LexerMachineState`/`ParserMachineState` публикуются через `ctx.set()`, а продолжения — через транзакционный `ctx.emit()`; исключение до Commit не публикует частично подготовленные состояния.
- Данные токенов и краткие уведомления о готовом узле заморожены. Готовый AST удерживается immutable Store.
- Повторное использование `createCParser()` допускается. Новая сессия сбрасывает стеки; после синтаксической ошибки можно начать заново.
- `maxTransitions` ограничивает количество шагов **отдельно** для лексического и грамматического этапа; ошибка лимита приводит к `failed` и `RangeError`.
- Реактивная цепочка при `parse()` синхронная (`execution: "inline"`). Большие файлы будут занимать поток до завершения; это тест выразительности Nexus, а не высокопроизводительный промышленный парсер.
- Состояние автомата использует `storage: "reference"` как оптимизацию удержания неизменяемых структур. Внешнему API не выдаются ссылки на эти внутренние Store.
- Существующий парсер и лексер остаются **только эталонной реализацией** для сравнительных тестов, а не частью реактивной цепочки.
